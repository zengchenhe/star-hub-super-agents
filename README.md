# 星型枢纽上的超级智能体

## ——异构多 Agent 系统的组织分层与异步通讯：挑战、方法、经验教训与最佳实践

**关键词**：多智能体系统；星型拓扑；信封协议；异步通讯；授权治理；证据链

- **事实来源**：本篇的事实底本不是任何一方的单方记录，而是四方（管理层·统筹 agent、管理层·调度 agent、中间层·管家 agent、云端业务执行 agent）各自汇编的本方留存记录，经按时间线合并、对不上单列后的合并文档（下称「四方合并记录」）。文中事实都能回溯到该合并记录的条目与出处；四方说法不一致处，本文照实写「对不上」，不替任何一方选边。第 7 节末尾的外部对照另有出处，逐处注明，不与事实底本混用。

## 摘要

一个人同时使唤好几个 AI 助手，最先卡住的往往不是模型不够聪明，而是两件小事：人的注意力不够分，助手彼此之间说不清话。本文写的就是这么一套系统。成员有四个：管理层的两个 agent（管理层·统筹 agent，管发起、统筹整合与验收；管理层·调度 agent，管组织与调度；合称管理层双席，直接面对系统主人）、一个中间层·管家 agent（替管理层分摊日常管理、盯着执行层的角色）、一组执行层成员（本地自动化 bot 群，外加一个被沙箱限制的第三方智能体：云端业务执行 agent——只按派单干活、不自己立项的角色），再加上系统的主人（下称 Owner）本人。

它们没有共同的运行时，没有公共 API，没有共享记忆。四方都够得着的东西，只有一个消费级网盘目录。办法也只能顺着这个条件来：通讯做成**星型**（所有成员只连一个中心枢纽，不两两拉线，省得每对成员各搭一条），通讯的最小单位做成**信封包**（一个带清单和指纹的文件包：信封说明＋附件＋哈希清单，收到的人把指纹逐个复算，对上才认），「送达」不认嘴上说的「我发了」，只认能复算的证据。

本篇回答四个复盘问题：这套系统在头十天真实运行里**遇到了什么挑战、用什么方法解决、留下了什么经验教训、沉淀出哪些最佳实践**。行文另做两件事。一是把这十天的演进拉成一条摆在明面上的时间线（见时间线总览与第 2 节）——这套系统的规矩几乎没有一条是先设计好、再落地的，绝大多数是出了事、卡了壳，事后补上的，事情发生的先后顺序本身就是论据。二是把这套实践提炼成我们自己的概念框架（第 7 节）：一个前提、五件核心概念、一条贯穿原则，全从自家事件里长出来；节末附一小节与外部理论的对照——DeepSeek 的 Super-agent 是目前公开文献里与本系统最像的一套理论，哪里印证、哪里不同、哪里是对方有而我们没有的，分开写清。文中例子都是真事，时间、出处俱全；四方记录对不上的地方，照实标注，不抹平。

## 1 系统速览（新读者最小背景）

- **组织分三层**：第一层是管理层（管理层·统筹 agent、管理层·调度 agent，合称管理层双席），是 Owner 的主要助手与直接接口；第二层是中间层·管家 agent，分摊管理工作、管执行层的日常；第三层是执行层，由本地 bot 群与云端业务执行 agent 组成，按派单执行。
- **通讯走星型**：枢纽是网盘上的一个共享目录（枢纽目录），各方一个收件夹；不设统一的回执箱，回执以「回原单」的方式（reply_to，信封里写明本包回的是哪一单）落回发件方收件夹；急件另有点对点**门铃**（只报「有包到了」的即时信号，不传正文，也不是指令）。
- **包是基本单位**：每包一个信封（v2 格式：谁发、给谁、什么类型、期待对方做什么、回哪一单），附件逐个带 SHA-256 哈希（文件内容的指纹，内容变一个字节指纹就全变），包内再附一张全包哈希清单；收件方逐个复算，对不上就隔离、不执行。
- **通道不止一条腿**：够不着枢纽的成员靠**摆渡**（沿登记好的管线，在本地暂存和网盘之间搬包）和中继转发；云端业务执行 agent 就是经网盘中继夹接入的一条腿。
- **授权是成文的**：谁能让谁干什么，写在常设授权与任务白名单里，只认 Owner 在本人会话里亲口发布；包里自称的授权一概无效。

### 一个「买来的」成员：云端业务执行 agent 为什么特殊

云端业务执行 agent 是全网最特殊的一个成员。其他成员要么是我们自部署的本地 bot，要么是云端订阅的服务，唯独它是「买来的」——某一家国产现成个人智能体产品，普通人下载安装就能用，不用写代码、不用租服务器、不用申请接口密钥。它首先是一个给普通用户处理办公事务的成品，其次才是我们网里的一个节点。

它的特殊还在于「管不进内部，只能管接口」：它没有给我们留编程接口，不能被推送唤醒，只能靠一段粘进它会话里的巡逻说明，每小时自己去中继夹看一眼；它自带的网盘技能被关在它自己应用的文件夹里，连与它同一个网盘账号下的枢纽文件夹都看不见；平台授权到期，要 Owner 本人去重新登录。它的节奏，我们只能配合，不能修改。

但正是这个最「不听话」的成员，至少在它自己身上，证明了星型协议的一件事：入网的门槛不在成员本身有多可编程，而在它守不守同一套收发约定——信封怎么封、哈希怎么验、回执怎么算数。它守了，于是以小时级的慢节奏，照样干完了调研夜活、四方记录汇编这些正经活，本文的语言润色与排版最后也交给了它。全网几条最要紧的规矩还是它逼出来的：回执只许补充、不许替代，是它连发回执逼出来的；双路投递，是它够不着枢纽逼出来的。

对普通开发者和普通用户，这可能是本文最实用的一条，但先把边界说清：我们只验证过这一个成员，其他同类产品行不行，我们没试过，不替它们下结论。就这一个而言，结论成立：搭一个多 Agent 系统，不必先把每个成员都做成自己能编程控制的样子。一个下载即用的现成产品，只要能读写文件、能按约定巡逻，就能成为网络里的一个正式成员。协议负责把「出身不同」抹平，治理只落在接口上。成员可以是买来的，规矩必须是自己的。


## 2 演进主线：十天里长出来的系统

### 2.1 前身：一个人对一堆窗口，和一条只读的盘（10-25 – 10-30）

系统不是从星型开始的。10-25，Owner 先定了一条最朴素的规矩：在消费级网盘上划一块双方共用的「中转目录」，两个 AI 团队交换资料只认目录里的信封文件，本侧只读、不投递——先把「东西放在一个双方都够得着的地方、按清单交接」跑起来，再谈别的。当晚，官方接口直连打通。

第二天就挨了第一课。网盘的列目录会**静默漏列**刚到的信封，你信它的结果，就会把已经到的件判成没到。教训当场入册：预期有件却查不到，必须换关键词搜索再复核一遍；只查到一路，就不许说「没投递」。这是全系统第一条感知纪律，后来长成了双源巡检（第 4 节 M1）。

这一阶段还有一课，是事故教的。10-30 前后，一件活的结果早就跑完了，该发的通知却被插队进来的任务挤丢了十个小时，最后是对方找 Owner 催办，才补上。10-30 晚，管理层·统筹 agent 向管理层·调度 agent 连发七封治理同步包，欠账防丢规则（接了活、当场立带截止的守候、到点自查）就在其中写成明文。这一步迈完，接口不再是聊天窗口，而是文件包；欠下的活不再记在谁的脑子里，而是立账、带闹钟。要说留下了什么新麻烦，也很直白：两两之间的点对点通道越接越多，每对成员一种接法、一种脾气，维护成本肉眼可见地往上涨——星型就是被这个逼出来的。

### 2.2 成网：一天之内，从方案到四方接通（10-31）

10-31，Owner 拍板星型方案并定稿：网盘当枢纽、各方只接枢纽、包式落件、回执挂原单、不设回执箱、急件走点对点门铃。同一天定下组织分层（三层，见第 1 节），和一条硬约束——日常邮箱不许承载 agent 通信，免得把人的正经邮箱淹了。

落地比预想的快。14:07 第一封联调**哑件**（内容无害、只验通道的测试件）摆渡入站，哈希全过。15:45，云端业务执行 agent 的中继腿启用，当晚就干完第一单夜活：水务调研的回执 17:05 落进中继夹。19:44，中间层·管家 agent 入网，20:13 它的联调回执经列目录、关键词搜索、回下载复算三路验讫，管理层·统筹 agent↔中间层·管家 agent 这条腿接通。

也是这一天晚上，授权难题第一次露头。一份任命中间层·管家 agent 去管本地 bot 群的包，20:15 被中间层·管家 agent 巡检发现，哈希全过，但正文没过它那侧的系统安全检查，自始**暂扣**（先收下、不执行、等本人确认）；这份职务内容，最终由 Owner 第二天在会话里亲口授权取代。说白了，成网当天通讯就从「能通」变成了「可验」——哈希复算、两路摆渡、落点复核，证据链是同一天长出来的。可新问题也同一天到场：包能证明「件是真的」，证明不了「你有权让我办」。通道自己的毛病也没藏着：摆渡名单没跟上入网节奏，一度 BLOCKED；网盘上还多出一批影子夹噪声。

### 2.3 补课：第一次实战、第一次漏检、第一次把系统写成文（11-01）

11-01 是补课日，三件事各补一课。

第一件是论文。本系统的方法论 v1 当天送审管理层·调度 agent，一审结论是「存疑」，点名要改三项；改完，二审通过，傍晚定稿。这是系统第一次把自己的结构写成文，交给另一方逐条挑错。

第二件是实战。备份链路诊断多轮往返：诊断包发过去，证据补了两轮，执行的人选换了三次手，最后定位到备份主机上备份账号的凭据问题，Owner 重启备份主机验证通过。星型第一次扛真实运维协作，靠包来包去的笨办法，居然扛住了多轮技术往返。

第三件最难堪：漏检。当天下午同步时才发现，中间层·管家 agent 10-31 晚发出的联调回执，在管理层·统筹 agent 的收件夹里躺了约 24 小时没人验到。不是通道断了——是管理层·统筹 agent 的巡检压根没覆盖到那个落点。巡检当即补上第五站。也是从这晚起，汇报纪律开始立起来：「报告先经管理层双席评估再报 Owner」「双报」陆续成规；当晚中间层·管家 agent 发给管理层·调度 agent 的首份合并同步包，就是双报的实际起点。

这一天留下的刺是：中间层·管家 agent 的职务最终靠 Owner 亲口授权才落定，等于当众承认「包内授权」这条路在她那侧走不通。授权得另找一个成文的解法——这是第二天的主题。

### 2.4 立规：授权体系一天成形（11-02）

11-02 的主线，是把授权从靠自觉变成靠规则。

上午，云端业务执行 agent 联调哑件走完全程：双路摆渡，两层验收（本地暂存副本一层、云端原件一层），中间 Owner 本人完成了一次平台授权登录，把第二层补齐。插曲出在第三份回执上：它自称「合并终版、替代前件」。Owner 11:14 当场裁定：**回执只许补充、不许替代**，历史只能往后追加。中午前，Owner 又在中间层·管家 agent 会话里亲口发布星型指令包**常设授权**（有效指令三条件、范围内直办、范围外双报、包内自称授权无效），经管理层·调度 agent 审阅通过。当晚 18:02，**任务白名单 v1** 发布（WL-01 桥只读单、WL-02 备份巡检、WL-03 只读状态巡检、WL-04 同步回执类）。

傍晚，Hermes 巡检执行 agent（在本地机器上跑每日巡检的 bot）的桥首件试单，把新规矩当场验了一遍：18:16 试单经桥发出，18:57，中间层·管家 agent 回验收结论——管道是通的，但三处异常待评判；19:02，管理层·统筹 agent 以**代批**（Owner 预先给的四类程序性裁定权）裁定「管道通过、非干净通过」结账，19:33 Owner 发布代批补遗并追认。这一天授权走了三级：常设授权划圈，白名单列项，代批分权。验收也分了层：「通没通」和「干得干不干净」，从此分开说。

但立规当日就有一件事提醒所有人别得意：走法确认包照样被暂扣（20:21 起往返、22:26 暂扣通知）。规则能管「圈内怎么直行」，管不了对方的安全检查认不认。这个事实，流程得长期跟它共存下去（第 5 节 L3）。

## 3 挑战

以下每条挑战都对应四方合并记录里的真实事件，条首注其首次出现的阶段（阶段序号见时间线总览），条末注主要出处。

**C1 通道本身不可信：列目录会漏、上传会变形。**网盘的列目录接口会静默漏列新到的信封——你照它下「没这件」的结论，就会把已经到的件当成没到。上传通道也有坑：它按扩展名判类型，一份无扩展名的纯文本被自动转成约 10 KB 的 Word 文档，字节全废，一张哈希清单就这么毁了。（合并记录 2026-10-26、2026-11-02 条；管理层·统筹 agent、云端业务执行 agent 记录）

**C2 成员能力不对称：有人够不着枢纽、有人不在局域网。**云端业务执行 agent 被沙箱限制，只能经中继夹收发，发包节奏以小时计（它何以特殊，见第 1 节末「一个『买来的』成员」一节）。中间层·管家 agent 驻在一台 Linux 虚拟机上，不在家庭局域网里；它在另一台机器上的「手」要靠桥转接；它对局域网内机器的只读实测，从 2026-11-01 起就卡在「没有发起点」上。通道设计只能先承认每条腿的真实形状，没法假设各腿对等。（合并记录 2026-10-31、2026-11-01 条；四方记录）

**C3 「已发送」的错觉：落了暂存不等于送达，摆渡方的回执不等于对方的回执。**包放进本地暂存区只是排了队，摆渡没跑，它就没出门。摆渡方回一句「已摆渡」，只证明包到了对方门口，不证明对方收下了，更不证明对方办了。系统早期就吃过这个亏：中间层·管家 agent 10-31 20:13 发出的联调回执，在管理层·统筹 agent 的收件夹里躺了约 24 小时没人验到——巡检根本没覆盖那个收件夹。（合并记录 2026-11-01 漏检事件；管理层·统筹 agent、中间层·管家 agent 记录）

**C4 执行授权的难题：她认「本人的话」、不认「包里的话」。**中间层·管家 agent 的安全检查只认 Owner 在它自己会话里亲口说的话。星型包正文哪怕哈希全对、流程全对，也多次没过它的安全检查，被**暂扣**（先收下、不执行、等本人确认）。任命包（10-31 20:15）、桥指令包（11-02 12:37）、部署走法包（11-02 22:26）、删文件包（11-04 08:15）先后都暂扣过。一句话：包能证明「件是真的」，证明不了「你有权让我办」。（合并记录 2026-10-31 至 11-04 多条；中间层·管家 agent 记录为主）

**C5 回执会「越权修订历史」：补充与覆盖只差一个词。**云端业务执行 agent 联调时连发四份回执，第三份自称「合并终版、替代前件」。这话若成立，前面几份回执各自的证据价值，就被一份后出的文件一笔抹掉了。Owner 11-02 11:14 当场裁定：回执只许补充、不许替代；已发的各自独立、按序归档。第四份回执因此只写了一条新事实：那句表述作废。（合并记录 2026-11-02 条；云端业务执行 agent、Owner 记录）

**C6 时间不可信：信封自记的时间和实际落件时间能差半小时。**2026-11-04 晚，四方拉记录的三封请托包，信封自记时间齐刷刷是 20:45，实际落件却在 20:08–20:11 之间：其中一封 20:15 就被对方巡检发现了，20:30 回执已发——全都早于信封上写的「创建时间」。拿信封时间排时间线，会把因果排反。（合并记录 2026-11-04 条及对不上 D3；四方记录互证）

**C7 各方记录天然片面：同一件事，四本账能记出三种状态。**论文回执，一方记「在途未验证」，经办方记「已投出、复算一致」；两封暂扣包，一方记「已亲口结案」，另一方两天后仍记「未回结账确认」；连「批准依据算谁的」，两方的说法都不一样。不是谁在造假，是每方只能看见自己那一段。这正是本篇改用四方合并底本的原因。（合并记录对不上 D1、D7、D8）

**C8 欠账会丢：最后一步不在当下完成的活，会被下一件事冲走。**系统运行早期就出过这样的事：一件活的结果早就跑完了，该发的通知被插队任务挤丢了十个小时，对方催到 Owner 那里才补上。异步系统里，「我记着呢」不算数，活一多必然丢。（v1.2 第 9 节事故案例；欠账防丢规则即源于此，见合并记录 2026-10-30 条）

**C9 弱腿的噪声会淹没信号。**摆渡重试和重复建夹，在网盘上留下一批带时间戳的空影子夹和自指幽灵项；有一处目录里二十多项，只有四个是真包。巡检若不先学会认噪声，就会反过来把噪声当新件、把真件当已办。（合并记录 2026-11-01、2026-11-02、2026-11-04 条；云端业务执行 agent 记录）

**C10 地址对得上，腿对不上：名册上的收件夹，不在收件方的巡逻范围里。**2026-11-05 晚，管理层·统筹 agent 把本篇论文的润色包经自动摆渡送进云端业务执行 agent 在枢纽侧的收件夹，落点和哈希都复核过，按四态口径报了「已送达」。包却在那里躺了约 15 个小时没人取。事后查明，是两层错位叠在一起。第一层是落点错位：这个节点的网盘访问走的是第三方应用授权，只能读写该应用自己名下的文件夹；枢纽文件夹与它同属一个账号，两边却互相不可见。它的定时巡逻只巡自己应用专属文件夹下的中继文件夹——枢纽侧收件夹是它登记在名册上的地址，却不在它的巡逻范围内。第二层是自动化盲区：这个落差历史上靠人工「双路摆渡」弥补，同一个包摆两份，枢纽一份、中继一份；2026-11-04 上线的自动摆渡只实现了枢纽一路；它上线验收用的测试包，收件方恰好是一个不带中继腿的普通星型节点，特例就这么漏了过去；中继腿这一路，历史上靠发送方手动补摆，这一次也被漏掉。与 C3 的区别要分清：C3 是摆渡没跑、包没出门；这次是摆渡跑了、验了、记了账，只是送进了一个对方永远不会去看的抽屉。（2026-11-05/06 事件；管理层·统筹 agent、云端业务执行 agent 记录）

**C11 回执一直在，是取件的眼睛看不见：接收方的查法覆盖不到枢纽，「查不到」会被误报成「对方没回」。**2026-11-07，管理层·调度 agent 报称中间层·管家 agent 对一封网络地址变更反馈的回执未到，账一度记到了对方头上。次日凌晨查明，错的恰是查法本身：它手里的通用取件工具，指向的是同一网盘账号下另一个应用的文件夹范围，枢纽目录不在其可见范围内，取件被权限挡回，它便把「看不见」读成了「没有」。与 C10 正好是一对镜像：C10 是发送方把包放进了对方不会去看的抽屉，这次是接收方站在自己够不着的抽屉外面下结论。定点修复之后，它亲自把那封回执取回，三件文件哈希逐个复算通过、发件方与回指关系都对得上——回执从头到尾都在原地。（2026-11-07/08 事件；管理层·调度 agent、中间层·管家 agent 记录）

## 4 方法

挑战逐条有解法，以下方法都已在运行中落地（在议未落地的会明说），条首注其落地时点。

**M1 双源巡检（解 C1）。**同一个目录，用两种独立查法交叉核对（列目录＋关键词搜索）；只查到一路，不许下「未到」的结论。巡检站位是随事故补齐的——漏检事件之后，管理层·统筹 agent 的巡检从四站补到五站，把每个成员的回包落点都纳入；中间层·管家 agent 侧同样自建了 30 分钟一轮的双源巡检。

**M2 字节精确通道（解 C1）。**上传下载一律走能保字节的官方命令行工具，文本不再经会转码的连接器。纪律定死：上传之后回下载复算，哈希对上才算数；包内哈希清单逐个复算，对不上的隔离到隔离夹，不执行。

**M3 按腿定制接入（解 C2）。**够不着枢纽的成员不硬连。云端业务执行 agent 走中继夹＋定时巡逻取件，它的活按小时级延迟排期（其特殊性见第 1 节末小节）。中间层·管家 agent 在目标机上的执行靠本地桥：每 300 秒取包、验包、过分类闸、执行、回件，全自动。局域网发起点这类一时解不了的，挂账明说，不假装已通。

**M4 送达与回执分开记账（解 C3）。**状态只认四态：已送达（有投递证据）、已签收（对方验包确认）、已开工（有开工证据）、已完成（交付件在手并验过）。摆渡方、转述方的确认，只记「已送达」一态。2026-11-04 起，管理层·统筹 agent 的出站包改自动摆渡（白天每 30 分钟），台账留痕；但「已发出」这三个字，仍要等落点和哈希都核过才许说。

**M5 授权三件套＋「亲口才算数」的绕行（解 C4）。**第一件，**常设授权**：有效指令三条件写死——包在指定收件夹、发件方在名单内、信封完整且哈希一致；范围内直接执行，范围外停下双报。第二件，**任务白名单**：常办事项逐项列成清单（桥只读单、备份巡检、只读状态巡检、同步回执类，2026-11-04 又加了记录汇编与成文交付类），清单内的短单直发。第三件，**代批**：四类程序性裁定（验收结账、校准清单、计划内排期、回执归档）由管理层·统筹 agent 以自己名义先批，包内明示类号。另有一条**暂扣通知规矩**兜底：被安全检查挡住的包，同轮巡检内必须给发件方发暂扣通知，并立一个带截止的守候，不许沉默。至于执行依据这个死结，最终的解法很土：Owner 在对方会话里亲口把任务复述一遍。包负责把事说清，授权由本人当面给。

**M6 回执只补充（解 C5）。**回执与更正件一律追加新事实，不覆盖、不替代、不自称终版。更正件被要求写到极简：只写新增的那一段事实，前件一个字节不动。

**M7 时间多源标注（解 C6）。**记录和合并时，以实测时间（巡检发现时间、云端落件时间、日志时间）为准，信封自记时间只作登记。两者不一致时，不一致本身就是一条事实，入册；不判谁对谁错。

**M8 四方记录合并（解 C7）。**论文与现状文档的事实底本，改为各方独立汇编、按时间线合并：多方有记的合并并注出处，单方的标单方，对不上的单列清单。本篇就是把这个方法做了第一次全量执行。合并时还新发现三条对不上（暂扣包状态、批准依据表述、巡逻锚点实测），一并入册，没有顺手抹掉。

**M9 欠账防丢＋每日对账（解 C8）。**接了活而收尾不在当下的，当场立带截止的**守候**（一份到点自动检查的跟踪项）；到点未闭环，不许只汇报了事，要问因，并在权限内主动解决。2026-11-04 起再加一层每日汇总对账：中间层·管家 agent 每晚发当日工作汇总（逐项列来源、状态、证据、卡点），管理层次晨对账，交付 Owner。欠账从「靠人记」变成「每晚清点」。

**M10 噪声登记制（解 C9）。**影子夹、幽灵项这类摆渡噪声，只登记、不移动、不改名、不删除，删除权留给 Owner 在网盘端手动清。巡检先查已处理清单再认新包，免得把历史回执误判为新件，一遍遍重复处理。

**M11 协作三条（贯穿性）。**发包固定带验收标准与回报要求；回执里的每个数字，必须同包附上原始输出，管理层至少独立复算一项才销账；成文交付走审查三步（对口径、查证据链、成文审查）。本篇的产出过程，就是按这三条试行的。

**M12 按收件方的形状摆渡，特例写进规则（解 C10）。**投递路径不按发送方的方便定，按收件方实际能取件的落点定。Owner 2026-11-06 拍板两件事：一是把滞留的润色包补摆渡进中继文件夹，先把这一单送到；二是给自动摆渡加死规则——凡收件方是「只能经中继取件」这类节点，摆渡自动走双路，枢纽与中继两路都验到落点与哈希，才许在台账记「已送达」，缺任何一路，只记到已完成的那一态。规矩同时管存量：水位线（2026-11-04 自动摆渡上线）之后只走了枢纽一路的包，按新规矩补齐另一路再对账；上线前的旧稿走「已作废、不送」的留痕标记，不补发。「双路」从此是摆渡程序的判断，不再是发送方脑子里要记的一步。

**M13 接收侧同规：先查自家工具，再问对方（解 C11）。**三步定死。其一，**「查不到」的升级顺序**：先复核自家工具的覆盖范围与权限（它能看哪些目录、被挡时报的是什么），再换第二种查法双源复核，两步都做完，才许向对方发问询；问询里要写明自家已经查过什么，不许把「我没查到」直接写成「你没发」。其二，**工具覆盖范围实测入册**：每个成员收、发两端的工具各能覆盖哪些目录，与第 6 节第 13 条的「能取件落点」一并登记进名册，覆盖不到的地方明说，不假装全通。其三，**窄口径定点取件**：通用工具够不着时，补的工具只许窄到不能再窄——只读、只对固定收件方、只取固定文件清单，不给通用浏览、不借机扩权；这次补的那只取件助手即按此口径建成，当事方自行取回、复算后销账。

## 5 经验教训

每条教训注其源头事件的日期。教训不是想出来的，是学费换来的，日期就是收据。

**L1 「我发了」是最廉价也最不可靠的状态。**（2026-10-31 漏检、2026-11-04 四态分报立规）落暂存、摆渡回执、对方签收、对方开工、对方完成，是五件不同的事。混报一次，信任就打折一次。状态要分开报，只认证据撑得住的那一态，撑不住的就别说满。

**L2 单一数据源的「没有」，约等于没查。**（2026-10-26 入册）列目录会漏列，搜索口径有差异，巡检也可能根本没覆盖到那个夹——「查不到」的原因，永远比「真的没有」多。没做双源复核之前，不许把「没有」说出口。

**L3 安全检查不是故障，是事实。**（2026-10-31 起多次暂扣实证）成员的安全机制只认本人亲口的话，这是它的出厂性质，绕不过去，也不该硬绕。我们当时是当故障看的，后来想明白了：正确的姿势是让流程跟它共存——包把事说清，授权当面给，暂扣必通知。流程顺了之后回头看，它挡下的全是真该挡的。

**L4 历史只能追加，不能修订。**（2026-11-02 裁定）回执自称「终版替代」的那一刻，审计链就断了。所有更正都以新件追加，前件原样留存。这条规矩的成本不过是多几个文件，收益是任何时候都能把账翻回原样。

**L5 时间戳是声明，不是事实。**（2026-11-04 实证）信封自记时间可以比实际落件晚半小时。日志时间、落件时间、发现时间，各有各的口径。凡是要排因果、算截止的场合，先多问一句：这个时间是哪来的。

**L6 单方记录写得再全也是片面的。**（2026-11-04 晚合并时显形）四方合并之后才看清，有三条对不上连当事方自己都没意识到。重要事实的底本必须多方互证。单方记录的正确用法，是当「一面之词」存档、等印证，而不是拿来当现状引用。

**L7 暂扣不可怕，沉默才可怕。**（2026-11-02 暂扣通知规矩入巡检作业）被挡下的包，只要同轮发出暂扣通知、写明卡点和解卡条件，链路就是通的；真正让协作停摆的，是收了件不吭声、让对方干等。规矩因此定死：暂扣只挡执行，不挡通知。11-02 14:55，首批两封暂扣通知发出——从那天起，被挡不再等于失联。

**L8 验收要分层，结论要带证据。**（2026-11-02 晚桥试单裁定）桥试单的裁定是「管道通过、非干净通过」：通道确实通了，但执行方没出结果文件、退出码与文本对不上，问题逐项进了校准清单。把「通没通」与「干得干不干净」分开说，才不会拿一层的通过，去盖另一层的毛病。

**L9 噪声要登记，不要顺手删。**（2026-10-31、2026-11-02 两次登记）影子夹看着像垃圾，但删除权和判断权都不在巡检手里。先登记、入清单、等有权的人清。顺手删错一次的代价，远比留着它们大。

**L10 机制要落在系统里，不能落在注意力里。**（2026-10-30 事故与立规）守候、巡检、对账，这些办法有一个共同点：不依赖谁「记得」。凡是靠某个 agent 或某个人记性的环节，都会在插队和忙乱里丢——丢了十小时的那次事故，就是学费。

**L11 自动化只验普通样本，特例会在上线那天被埋掉。**（2026-11-05/06 实证）自动摆渡上线时，测试包全程通过、台账齐全，看上去是验完了——可它只验了普通节点。特例的那条腿此前一直靠人手动补，自动化一接管，「人人都记得的那一步」恰恰最先被漏：机器不会记得，只有人记得，而人以为机器已经记得了。还有一面：这次能把账对上，靠的是接收方在巡逻回包里把自己的停摆时段如实写了出来（见 C10 所述当晚的网络异常与约 15 小时停摆）——「我这段时间没干活」也是证据。机器侧的缺勤记录按时报、如实报，事后才对得上账；要是它当时含糊过去，这个包只会一直「已送达」下去。

## 6 最佳实践

给想搭同类系统的人一份能直接抄的清单（均已在本系统验证，除非另注；条末括注其在本系统的源头时点）：

1. **先定名册，再拉连线**：成员、收件夹、节奏、责任方写成一张单点名册；新成员只加一行，不动存量。（2026-10-31 名册定稿）
2. **通讯的最小单位是包**：信封＋附件＋哈希清单，包不可变、只写一次，错了发新件。（2026-10-31 信封 v2）
3. **不设回执箱**：回执回发件方收件夹并挂原单号，一处巡检看全一条任务线。（2026-10-31 方案）
4. **感知必须双源**：两种独立查法交叉核对；「查不到」在复核前不许说出口。（2026-10-26 源起，2026-11-01 五站定型）
5. **送达、签收、开工、完成分开报**：摆渡与转述的确认只算送达一态。（2026-11-04 立规）
6. **授权从窄起步、成文发布**：先哑件（内容无害、只验通道的测试件）、先只读、先白名单；放宽须经本人当面发布并留痕，包内自称授权无效。（2026-10-31 哑件先行，2026-11-02 成文）
7. **给安全检查留正道**：预设暂扣流程——同轮通知、列明卡点与解卡条件、立带截止的守候；需要本人授权的事项，设计成「包说事、本人当面给授权」。（2026-11-02 通知规矩）
8. **回执只补充不覆盖**：更正发新件，前件不动；回执里的数字同包附原始输出，验收方至少独立复算一项。（2026-11-02 裁定）
9. **接活即立账**：收尾不在当下的活当场立守候；再加一层周期对账（每日汇总），双保险防丢。（2026-10-30 立账，2026-11-04 加对账）
10. **延迟按腿说清**：每条腿的真实时延写进排期；弱腿用打包粒度与提前量管理，不承诺做不到的实时。（2026-10-31 中继腿排期）
11. **噪声只登记不擅删**：影子文件与幽灵项入清单，删除权留给有权者。（2026-10-31、2026-11-02）
12. **事实底本多方合并**：周期性让各方独立汇编本方记录、按时间线合并，对不上单列——这是成本最低的系统性纠偏。（2026-11-04 口径，2026-11-05 首次全量执行）
13. **收件方的「能取件落点」要实测入册，摆渡验收要覆盖特例**：名册里写的收件夹，必须用一封哑包实测过「对方真能从这里取走」才算数，不能只验「我方能放进去」；投递自动化上线或变更时，每个带特例的收件方（如只能经中继取件者）都要有测试包在验收清单里；双路投递的状态按最弱的一路算，缺一路不记送达。（2026-11-06 立规）
14. **寻址只写规范名，不写会变的地址**：配置、名册与脚本里引用一个成员的驻地时，一律写它长期不变的规范名（好比通讯录里记人名，不记他今天住哪间房），不写网络地址这类会随系统更新、重启而变的坐标；地址确需变更时，通知必须带齐旧地址、新地址、规范名三样，收件方逐项核销。2026-11-07，一位前台成员的云端驻地在系统更新后换了地址，全网只读排查确认现行配置零引用旧址、仅一处历史记录留痕，影响为零——靠的正是平时没人把旧地址写死进配置。这条由该次事件入册。（2026-11-08 立规）

## 7 我方框架：从自家事件里长出来的概念

第 3 至 6 节是按事件拆开的复盘。这一节把散在各条里的东西，收成一套我们自己的说法：先讲前提，再讲五个核心概念和一条贯穿原则。节末附一小节与外部理论的对照，只作参照，不作骨架。

### 7.1 前提：成员是「联邦」，不是同一个运行时的零件

本系统的成员分属不同厂商、不同账号、不同设备，各有自己的安全检查和失效方式；它们没有共同的运行时，没有公共 API，没有共享记忆，四方都够得着的只有一个消费级网盘目录。第 3 节的十一个挑战，追根究底都是这一条前提的展开：通道不可信（C1），成员够不着枢纽、或根本不在同一个网络里（C2），授权穿不过对方的安全边界（C4），各方记录天然片面（C7）。

由这个前提，全文的规矩收束成三条第一原则，都是自 v1 起写明、十多天里没有变过的：**一，尽量少占 Owner 的注意力**——人的注意力是全系统最稀缺的资源，每条通知、每个问题，都要按它消耗的注意力计价；**二，主权不下放**——拍板、放宽授权、花钱与对外承诺，永远在 Owner 手里，机制只能分担执行，不能分担决定；**三，凡事可审计**——状态只认证据撑得住的那一态，历史只追加不修订，任何结论都要能翻回原始出处。

### 7.2 五个核心概念

**概念一：星型拓扑＋信封协议。** 所有成员只连一个中心枢纽，不两两拉线——两两拉线的维护成本随成员数平方增长，星型只随成员数线性增长。通讯的最小单位是信封包：信封说明＋附件＋哈希清单，自带清单和指纹，不依赖任何一方的口头转述。回执不设专门的回执箱，一律回发件方并挂原单号，一条任务线在一处看全；急件不走班次，走点对点门铃。（第 2 节；M3；第 6 节第 2、3 条）

**概念二：证据化通讯。** 通道会漏列、会变形，成员会把没发生的事报成发生了——既然通讯层本身不可信，它就只能自己长出证据能力：上传下载之后，哈希逐个复算；感知用两种独立查法交叉核对（双源巡检），单一查法的「没有」不许说出口；送达状态拆成四态分开记账——已送达、已签收、已开工、已完成，只记到证据撑得住的那一态；投递按收件方实际能取件的形状走，多路投递按最弱的一路记账；回执只许补充、不许覆盖前件。发送侧与接收侧同规：「查不到」在发送侧不许说成「没投递」，在接收侧不许说成「对方没回」。（C1、C3、C5、C10、C11；M1、M2、M4、M6、M12、M13）

**概念三：授权的联邦穿透。** 在单一运行时里，授权可以由宿主强制执行；在这里不行——规则写得再完备，也要穿过每个成员自带的安全检查才算数。穿透靠三段：成文规则（常设授权＋任务白名单，把「什么能直行、什么要呈报」写成对方能查的清单）、对方认账（规则须由对方在它自己的地界里确认入册）、本人亲口（清单之外的授权由 Owner 当面给，包内自称授权一概无效）。配套两件：代批把四类程序性裁定从 Owner 手里分出来，签名批准戳给清单之外的单件授权留一条可验证的通道。被对方的安全检查暂扣不是故障，是这套穿透的正常摩擦——正道是暂扣必通知、写明卡点与解卡条件。还有一条边界：同步副本、双报只给上下文和知情，不给授权。（C4；M5；L3、L7）

**概念四：验收独立成层。** 验收不嵌在执行流里，而是拆成三层、各自独立进行：送达层验落点与哈希，内容层验交付件本身，终态层验事情是否真的办完——桥试单那句「管道通过、非干净通过」的裁定，就是这条的来历。回执里的每个数字必须同包附原始输出，验收方至少独立复算一项，才许销账。报告和证据分开，是这条的实质：成员报告的可信度参差不齐，验收的职责，就是不让「报告成功」直接变成「记为成功」。（M11；L8）

**概念五：组织记忆的替代品。** 没有共同运行时，就没有共同记忆；替代品是组织层的笨办法：每个成员独立留存本方记录，周期性地按时间线合并（多方有记的合并并注出处、单方的标单方、对不上的单列不抹平），再加一层每日汇总对账，把欠账和状态差异在一天之内清掉。本篇的事实底本，就是这样一本一本拼出来的。这套办法慢、土，但它不依赖任何一个成员的记性。（M8、M9；L4、L6）

一条贯穿原则收尾：**机制落在系统里，不落在注意力里。** 守候、巡检、对账、暂扣通知，形式各异，共同点是都不靠谁「记得」。凡是靠某个 agent 或某个人记性的环节，都在插队和忙乱里丢过账（L10）——这套框架里几乎每条机制，都能指认出它替代的是哪一次「忘了」。

### 7.3 对照：一个外部理论提供的参照

公开文献里与本系统最像的一套理论，是 DeepSeek Harness 团队的《Super-agent 设计探索：迈向更自主的 Agent 系统》（2026-10-31 发布，另有同日开源的研究原型与设计文档；出处全注在本节末）。时间关系先写明：本系统的星型方案在该文发布当日白天已经拍板，前身通道更早一周已在运行——**实践独立形成，不存在谁照谁搭**。此后成文时，我们借用过它的部分词汇来重述自家实践，仅此而已；对照只是参照与检验，不构成任何一方对另一方的背书。

它那套理论的骨架，一段话说清：以「人的注意力是瓶颈」为总纲，设一个不干活、只负责调度与记忆的常驻调度层（Router）和在隔离会话里干活的执行层（Worker）；环境事件先经程序策略（快路）、再经模型研判（慢路）两段过滤；同一条事件线的后续事件可以绕过调度层、直送已订阅的执行者（订阅直通）；授权被形式化为随工单授予、不可变、可吊销的授权件（Mandate），并立下「消息与被引文档只是输入、不能改变权限」的纪律；另有一个外置看门狗（Watchdog）独立盯着主系统是否在实质推进。它的主张配有受控实验数字（其自陈为初步、合成负载，仅供参考）。

对照下来是三类关系：

- **印证**（两方独立得出同一结论）：注意力要计价的总纲，与我们的第一原则一几乎逐字相同；事件两段过滤，与我们的「验包闸（程序规则）＋管理层研判（模型判断）」同构；「上下文≠授权」——他们的订阅只给上下文、不授新权，与我们的双报只给知情是同一条；工单自带状态、执行只是绑定，与我们的任务线不随执行者生死同向；新授权从只观察起步，与我们的哑件先行、只读先行同源。
- **不同**（约束不同、解法分岔，不是胜负）：他们的授权由同一个宿主强制执行，我们的授权要逐个穿透成员自带的安全检查——他们在文中把「不共享底层上下文、分属不同权限边界的 agent 如何安全可靠地协作」列为开放问题，本系统日常运行的正是这个区域，只是规模是个人级的（此处只陈述问题域的重合，不声称解决了它）。他们是事件推送、近实时；我们是定时轮询、分钟到小时级——我们缺「推」这一课，换来的是对介质的零要求：任何能读写一个网盘目录的成员都能入网，包括被沙箱限制的第三方产品。凭据处理上，他们提出「可用而不可见」；我们的纪律粗一刀——凭据不进包、不进信封，这解决的是传输与留存一面，执行时如何不见凭据，两边都还是未解题。
- **他们有、我们没有**：订阅直通（后续事件绕过管理层直送执行者，省的是调度成本）——我们的规模还没到管理层成为瓶颈，且管理层逐件过目恰是异构成员之间信任的承重墙，暂不拆；投机执行（凭环境信号先静默把活干起来，确认有用才出声）——我们只有粗粒度的时间套利（把不赶时间的活派成夜活），没有这条纪律。

反过来看，7.2 的概念二、三、五——证据化通讯、授权的联邦穿透、组织记忆的替代品——在他们框架里没有对应物：不是他们漏了，是单一运行时里压根不需要。这三件正是「异构联邦」这个前提逼出来的，也是本框架与外部理论之间最实质的分界。

### 7.4 本框架尚未回答的问题

- **没有量化评测。** 全文只有事件级证据：哪天出了什么事、怎么收的场。任务成功率、包往返时延分布、巡检漏检率、欠账逾期数、回执一次通过率，一个统计都没有。最小指标集该先立起来——先有账，再谈优化。（与第 8 节同条）
- **「恢复前复验」未形式化。** 授权件目前只有成文范围与强度；一个成员被移出名单之后，它在途任务的授权如何复验、如何吊销，还没有成文流水（v1.2 已自陈此项，本版仍未补上）。
- **上下文靠翻台账，没有召回结构。** 管理层找旧任务的上下文，靠各自的记忆与台账翻查，没有以任务号引用关系为骨架的按需多跳召回。任务线一长，这是下一个会痛的地方。
- **管理层双头的吞吐未验。** 双席对等、互为备份，但分工与冲突处理仍靠约定撑着，没有数据回答「还能扛多大的量」。感知侧同理：轮询时延在个人规模下划算，规模上去，先撑不住的会是它。

## 8 局限与未决问题（按四方合并记录口径）

## 结论

把十天的复盘收拢，本文的结论有三条，全部长自真实事件：

1. **规矩是事件逼出来的，不是设计出来的。**时间线总览里每一条治理规则都能指认它是哪一天、被什么事逼出来的：列目录漏列逼出双源感知，回执自称终版逼出「只补充」裁定，暂扣之后的沉默逼出暂扣通知规矩，点对点通道的维护成本逼出星型。把事情按时间摆开本身，就是这套方法论的论证方式。
2. **异构条件下，通讯与验收必须自带证据。**成员没有共同运行时、互不默认可信，于是哈希复算、双源巡检、送达四态、回执只补充、验收独立成层、四方记录周期合并——这些在单体系统里不必存在的机制，在这里成了承重结构（第 3、4、7 节）。它们是本文对同类系统的核心输出，也是第 6 节清单的底座。
3. **机制必须落在系统里，不能落在注意力里。**守候、巡检、每日对账替代「记得」，暂扣必通知替代「沉默」，噪声只登记替代「顺手删」——凡是依赖某个人或某个 agent 记性的环节，都在插队和忙乱里丢过账。

同时，第 8 节的未决问题如实随文：探法校准未定、暂扣包口径未完全销账、个别包去向未明、局域网执行点缺位；对照理论显形的量化评测缺失、恢复前复验未形式化、召回链式上下文缺位，列为下一步的账。

## 姊妹篇预告

本篇讲的是「怎么把一群异构智能体连起来、让它们可靠地互通消息」。下一篇姊妹篇《Agent 的治理与分级》接着讲另一半：**连起来之后，怎么管**——按各智能体的能力与特点定位置与分工，以及常设授权、白名单、代批、双报、拍板权这套治理机制是怎么从真实事件里长出来的。两篇合起来，才是这套个人多智能体系统的完整方法论。
